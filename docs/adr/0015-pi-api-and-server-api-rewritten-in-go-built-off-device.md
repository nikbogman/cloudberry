# The Pi API, Server API, and their shared libraries are rewritten in Go, built off-device like the Caddy binary

`services/pi-api`, `services/server-api`, and `services/shared` (`control-plane-shared`) were rewritten from Flask/Python to Go, with no behavioral change: same endpoints, same status codes, same event-logging contract, same startup safety checks. The shared library split into two packages rather than staying one, since its two halves aren't actually the same concern: `services/internal/tailnet` (identity-header auth, bind-safety — both genuinely tailnet concepts) and `services/internal/eventlog` (the Grafana Cloud logger, which has nothing to do with tailnets — it's a logger that happens to be used by tailnet-fronted apps). Go's `internal/` visibility is the direct equivalent of "not a standalone service, a library dependency" from the old README. The two apps' own logic lives in `services/internal/piapi` and `services/internal/serverapi` (each package's primary file is `handler.go` — the idiomatic Go name for "defines the HTTP handler type and its constructor," in place of the old `app.py`/`wake.go`/`server.go` naming), with thin `services/cmd/pi-api/main.go`/`services/cmd/server-api/main.go` entrypoints doing only environment parsing and wiring. All packages share one Go module rooted at `services/` rather than one module per package with `replace` directives — less ceremony for code this small, at the cost of not mirroring the old per-package `pyproject.toml` structure exactly. Tests stay beside the code they test (`*_test.go` in the same package directory) rather than in a separate tests tree — the standard Go convention, and specifically why the handler logic lives in `internal/` at all rather than directly in `cmd/`: it lets tests exercise `handleWake`/`handleSuspend` directly via `httptest` without going through `main.go`.

This forced a deploy-model change beyond the language swap. `pyinfra/api_deploy.py`'s `git_systemd_service` helper — git-pull the repo to the device, `uv sync`, run `uv run flask ... run --host --port` — has nothing left to do once there's no interpreter, no dependency tree, and no source tree to check out: a Go build produces one static binary. `deploy_pi_api.py` and `deploy_server_api.py` now use a new `pyinfra/go_deploy.py` helper (`go_binary_systemd_service`) that cross-compiles on the dev machine and ships only the binary via `files.put`, running it directly as `ExecStart` with no `WorkingDirectory` — the same off-device build-then-ship shape ADR-0013 established for the `wake_plugin`-enabled Caddy binary, now extended to both control-plane apps. `templates/binary.service.j2` replaces `templates/api.service.j2` (dropped, now unused) for this simpler unit shape; `templates/binary.service.j2`'s pattern deliberately mirrors `templates/caddy.service.j2`'s "run a shipped binary from `/usr/local/bin`" convention. This supersedes ADR-0006's git-pull-deploy default specifically for these two apps — it doesn't touch ADR-0007's systemd-not-Docker decision, which is unaffected either way.

The Pi API's build stays hardcoded to `GOOS=linux GOARCH=arm GOARM=6` (the Pi Zero W is a fixed, known device, same reasoning and same constant ADR-0013 already pins for the Caddy build). The Server API's build does not hardcode `GOARCH=amd64`: `server` could plausibly be amd64 or arm64 hardware, and `deploy_docker.py` already avoids exactly that assumption for its apt-repo `arch=` line via a `DpkgArchitecture` custom fact (`dpkg --print-architecture`). We moved that fact from `deploy_docker.py` into `common.py` — it now has two real consumers — and `deploy_server_api.py` maps its result to a `GOARCH` (`amd64`→`amd64`, `arm64`→`arm64`), raising rather than guessing if the device ever reports something else. The Server API is still built off-device even though the main server isn't resource-constrained the way the Pi Zero W is: consistency (one build path for both Go services) outweighed the marginal convenience of an on-device `go build`, and it keeps a Go toolchain off a machine that would otherwise carry one solely for this.

`PI_API_PORT`/`SERVER_API_PORT` are new required-by-convention (defaulted) environment variables read directly by each Go binary's `main.go` — previously the port was a `flask run --port` CLI flag baked into `start_command`, but a Go binary has no wrapper command to bake a flag into, so the port moved into the same environment-variable config surface as everything else.

Consequences:

- `pyinfra/api_deploy.py` is deleted (no other caller); `settings.DeploySourceSettings` (`homelab_repo_url`, `deploy_ref`) is deleted with it, since it existed only to parameterize that helper's git-pull.
- Neither `pi` nor `server` needs this repo git-cloned on-device anymore for these two apps. Nothing else was found depending on `/srv/homelab` existing on either device — the UI's `dist/` is synced from a dev-machine build (`deploy_pi_api.py`) and Caddy's config is templated from local files (`deploy_caddy.py`), neither via an on-device clone.
- `common.DpkgArchitecture` is now shared by `deploy_docker.py` and `deploy_server_api.py`; its docstring was updated to describe both callers.
- Every Python test in `pi-api/tests/`, `server-api/tests/`, `shared/tests/` has a direct Go analogue (stdlib `testing` + `net/http/httptest`, no mocking framework — hand-written fakes for the `Waker`/`EventLogger`/`Suspender` seams). The old Python directories (`pyproject.toml`, `uv.lock`, `src/`, `tests/`) are deleted once the Go versions were verified against them.
