# The Caddy binary is cross-compiled off-device and shipped by pyinfra, not hand-built on the Pi

`deploy_caddy.py` now builds the `wake_plugin`-enabled Caddy binary on the dev machine with `xcaddy`, cross-compiled for the Pi Zero W (`GOOS=linux GOARCH=arm GOARM=6`), and ships only the compiled binary to `pi` via `files.put` — the same off-device-build-then-ship shape ADR-0006 already established for the UI's Vite build. This closes the gap `pyinfra/README.md`'s "Known gaps" section and `services/pi-proxy/wake_plugin/README.md` previously flagged: provisioning the binary was a manual, undocumented prerequisite. We rejected building on the Pi itself for the same reason ADR-0006 rejected an on-device Node toolchain: the Pi Zero W is single-core and low-memory, and neither Go nor `xcaddy` need to ever run there. This adds a new dev-machine prerequisite (Go + `xcaddy` installed locally, alongside the Node/npm the UI build already requires) — not free, but consistent with the existing precedent rather than a new kind of cost.

This also required deciding how `caddy.service` itself gets onto the device, since no systemd unit for it existed anywhere in this repo before this change either (the prior "manual prerequisite" implicitly covered both the binary and, presumably, an apt-installed `caddy` package's unit file). We chose a pyinfra-owned unit template (`templates/caddy.service.j2`, installed to `/etc/systemd/system/caddy.service`) over continuing to rely on `apt install caddy` for it. Rejected that alternative because it would leave the binary pyinfra ships fighting the identical path (`/usr/bin/caddy`) dpkg thinks it owns — a package-manager-vs-pyinfra split-brain over the same file. The pyinfra-owned unit runs the shipped binary from `/usr/local/bin/caddy` instead (the FHS convention for locally-installed, non-package-managed software), so there is no dpkg-tracked path involved at all, and the unit itself is now templated exactly like `templates/api.service.j2` already is for the Pi/Server APIs (ADR-0008's "nothing hand-edited on the device" logic, extended to this unit too).

`caddy.service` runs as `root` (`run_as_user="root"`, mirroring `api_deploy.git_systemd_service`'s own default for the Pi/Server APIs) rather than a dedicated unprivileged `caddy` system user. A non-root user was considered and built first, then dropped to match this repo's existing convention rather than introduce a second, inconsistent privilege model alongside the Pi/Server API units — deliberately not a hardening regression this repo already accepts elsewhere, just consistency with it.

`templates/caddy.service.j2` was checked directly against the official reference unit (`caddyserver/dist/init/caddy.service`, linked from https://caddyserver.com/docs/running#using-the-service) and matches it apart from two deliberate deviations already covered above: `User=root` in place of the official `User=caddy`/`Group=caddy`, and the `{{ binary_path }}`/`/usr/local/bin/caddy` template variable in place of the official example's hardcoded `/usr/bin/caddy`. `AmbientCapabilities=CAP_NET_ADMIN CAP_NET_BIND_SERVICE` is dropped for the same reason as the non-root user — it exists to grant an unprivileged user network capabilities root already has unconditionally. Everything else (`Type=notify`, the `run`/`reload --force` commands, `After=network.target network-online.target` + `Requires=network-online.target`, `TimeoutStopSec=5s`, `LimitNOFILE=1048576`, `PrivateTmp=true`, `ProtectSystem=full`) matches the official unit verbatim.

Consequences:

- New dev-machine-only settings pinned as plain constants in `deploy_caddy.py` (`GOOS=linux GOARCH=arm GOARM=6`), not `settings.py` env vars — this is a build-target fact about the physical Pi Zero W, not a per-environment operator choice. Moving to a Pi Zero 2 W means editing this constant, not setting an env var.
- `deploy_caddy.py` provisions `/etc/caddy` (previously assumed to already exist) but no dedicated system user or data directory, since caddy runs as `root` like the other two units.
- Restart-vs-reload gating (mirroring `api_deploy.git_systemd_service`'s "restart iff something that requires it changed" rule) treats a binary or unit change as requiring a full restart, and a Caddyfile-only change as reload-eligible — restarting on every config edit would be a regression from the reload-only behavior ADR-0008's Caddyfile templating already had.
- `pyinfra/README.md`'s "Known gaps" bullet about the Caddy binary is resolved; `services/pi-proxy/wake_plugin/README.md`'s manual `xcaddy build` command is kept only as the reference for running the same build by hand outside pyinfra.
