# Control-plane events ship straight to Grafana Cloud's Loki endpoint — no self-hosted agent

`8fae71b` removed the original `AlloyLogger`/`ALLOY_PUSH_URL` wiring because Alloy was never actually provisioned by this repo — no dashboards, no alerts, and no ADR behind it, just a push URL wired into two stateless Flask apps with nowhere real to send events to. This ADR restores event shipping, but not via Grafana Alloy: Grafana Cloud doesn't run a hosted Alloy instance on your behalf (Alloy is always a self-hosted collector you deploy and operate yourself; Grafana Cloud's "Fleet Management" only centrally manages the *config* of instances you're still running). For a single-operator homelab, standing up and maintaining a whole agent process just to receive a handful of low-volume events isn't worth it, so pi-api and server-api now POST directly to Grafana Cloud's free-tier Loki push endpoint instead. Dashboards and alerts are deliberately still out of scope for this change — the goal here is only to get `wake_requested`/`wake_failed`/`wake_succeeded` (pi-api) and `suspend_requested`/`suspend_failed`/`suspend_succeeded`/`reachability_changed` (server-api) flowing somewhere queryable in Grafana Explore. Building curated dashboards is left for whenever there's an actual question those events need to answer.

While restoring the old `AlloyLogger`, we found it would never have worked against a real receiver: it POSTed an ad-hoc `{event_type, outcome, identity, extra}` JSON body to a URL shaped like Loki's push API (`.../loki/api/v1/push`), but that isn't a valid Loki push payload (Loki expects `{"streams": [{"stream": {...labels}, "values": [[timestamp, line]]}]}`). This went unnoticed because `send_event` deliberately swallows transport/HTTP errors so a logging failure can never break the caller's actual action — a malformed-but-still-a-string body would have failed silently rather than raised. The renamed `GrafanaCloudLogger` (`services/shared/src/control_plane_shared/grafana_cloud.py`) now emits a real Loki push payload: `event_type`/`outcome`/`app` as stream labels (low-cardinality, safe to index on), `identity`/`extra` JSON-encoded into the log line itself (`identity` is unbounded-cardinality, wrong shape for a label). It authenticates with Grafana Cloud's own Loki basic-auth credentials (username = the stack's numeric instance/user ID, password = an Access Policy token scoped to `logs:write`) directly on the request, since there's no local agent to hold them instead.

Consequences:

- New required dev-machine env vars on *both* the pi-api and server-api deploys: `GRAFANA_CLOUD_LOKI_URL`/`GRAFANA_CLOUD_LOKI_USER`/`GRAFANA_CLOUD_LOKI_API_KEY` — same env-var-only secrets convention as ADR-0010, nothing written to a file in this repo. Duplicated across both apps' secrets classes rather than shared, since each is deployed and configured independently (same reasoning `pyinfra/settings.py` already applies elsewhere: one settings class per Deploy file's needs).
- Both Flask apps now hold real Grafana Cloud credentials directly, and there's no local retry/buffering layer if Grafana Cloud is briefly unreachable — `send_event`'s existing "log and swallow" behavior means a transient outage now means a dropped event, not a queued one. Accepted: these are low-stakes audit events (Wake/Suspend/reachability), not anything requiring delivery guarantees.
- No dashboards or alerts exist yet — Grafana Cloud's free-tier retention window is the only thing giving these events any real durability. Revisit this ADR (or write a follow-up) once there's an actual dashboard/alert to add, so this doesn't quietly become the same "provisioned but unused" state that got the original wiring removed.
- No new pyinfra Deploy file, systemd unit, or apt package is introduced by this change — `deploy_pi_api.py`/`deploy_server_api.py` just gained three more environment variables each.
